# Concurrent Cinema Booking System

A compact TSOA/Express API for cinema shows, seats, and temporary
reservations. It demonstrates safe concurrent booking with PostgreSQL row
locks and expires unpaid holds using a BullMQ cron worker backed by Redis.

## Architecture

```text
Client
  │ HTTP / JSON
  ▼
Express bootstrap (src/main.ts)
  ├── JSON body parser
  ├── Auth rate limiter (/api/auth/*)
  └── TSOA-generated routes
        └── Decorated controllers
              ├── Auth controller → auth service (bcrypt + JWT)
              ├── Show and seat controllers → TypeORM repositories
              └── Reservation controller → reservation service
                    └── PostgreSQL transaction + SELECT FOR UPDATE

BullMQ cron schedule in Redis
  └── Expiry worker
        └── PostgreSQL transaction: HELD → EXPIRED
```

TSOA's JWT security handler protects reservation routes. PostgreSQL is the
source of truth; Redis stores the recurring BullMQ schedule, not booking data.

### Booking lifecycle

1. A client registers or logs in and receives a JWT.
2. The client sends that JWT in the HTTP Authorization header when requesting
   a seat hold.
3. The reservation service opens a transaction, locks the requested seat rows,
   checks for active holds or confirmed reservations, then creates a `HELD`
   reservation and its seat links.
4. A hold expires after 15 minutes. It can be confirmed or cancelled before
   expiry.
5. A BullMQ cron worker checks every minute and marks overdue `HELD`
   reservations as `EXPIRED`.

The row locks serialize requests for the same seats. The active-reservation
check rejects a request if another transaction has already committed a hold.

## Requirements

- Node.js
- pnpm
- Docker Desktop with Docker Compose

## Run locally (PowerShell)

1. Install dependencies:

   ```powershell
   pnpm install
   ```

2. Copy `.env.example` to `.env` and set `JWT_SECRET` to a long random value.
   Keep `.env` private.

3. Start PostgreSQL and Redis:

   ```powershell
   docker compose up -d
   docker compose ps
   ```

   PostgreSQL is published on `127.0.0.1:5433`; Redis is published on
   `127.0.0.1:6379`. Named volumes persist data. `docker compose down` keeps
   the volumes; `docker compose down -v` removes them.

4. Create the database schema:

   ```powershell
   pnpm migration:run
   ```

5. Start the API and expiry worker in separate terminals:

   ```powershell
   pnpm dev
   ```

   ```powershell
   pnpm worker:dev
   ```

   The API generates TSOA routes before starting. The worker registers the
   `expire-overdue-reservations` cron schedule in Redis.

6. Build and run the tests:

   ```powershell
   pnpm build
   pnpm test
   ```

With the API, PostgreSQL, and Redis running, run the HTTP smoke test in
another PowerShell terminal:

```powershell
pnpm test:api
```

Pass a different API URL if needed:

```powershell
pnpm test:api -- -BaseUrl "http://127.0.0.1:3301"
```

The smoke test checks health, registration/login, authentication enforcement,
seat creation, duplicate-seat booking rejection, confirmation, and
cancellation. It creates a unique user, show, seats, and reservations; those
records remain in the database.

`pnpm test` runs the database integration test only when `TEST_DB_DATABASE` is
set. Use a dedicated disposable test database. It will be migrated and used
for test records:

```powershell
docker compose exec postgres sh -c 'createdb -U "$POSTGRES_USER" cinema_booking_test'
$env:TEST_DB_DATABASE = "cinema_booking_test"
pnpm test
```

Generate the OpenAPI document with:

```powershell
pnpm openapi
```

The generated specification is `public/swagger.json`.

## API

| Method | Route | Purpose | Authentication |
|---|---|---|---|
| `GET` | `/api/health` | API and database status | No |
| `GET` | `/api/shows` | List shows and seats | No |
| `POST` | `/api/shows` | Create a show | No |
| `GET` | `/api/shows/:showId/seats` | List seats for a show | No |
| `POST` | `/api/shows/:showId/seats` | Add seats to a show | No |
| `POST` | `/api/auth/register` | Register and receive a JWT | No |
| `POST` | `/api/auth/login` | Login and receive a JWT | No |
| `POST` | `/api/reservations` | Hold seats for 15 minutes | JWT |
| `POST` | `/api/reservations/:reservationId/confirm` | Confirm a live hold | JWT |
| `POST` | `/api/reservations/:reservationId/cancel` | Cancel a live hold | JWT |

Register or log in to receive a JWT. Include it in the request's
`Authorization` header in this form:

<code>Authorization: B&#101;arer &lt;token&gt;</code>

The HTML entities in the example render as the standard HTTP auth scheme
followed by the JWT. The authenticated user ID comes from the token, not the
request body. Login/register requests are limited to 10 per IP every 15
minutes.

## Scope

- Confirmation changes the reservation state; it does not process payment.
- Show and seat creation are currently unauthenticated. Do not expose this API
  publicly as-is.
- There is no Redis cache or production deployment setup.
